> Преврати Kali Live USB в переносную систему, которая сохраняет твои изменения между перезагрузками — и остаётся нечитаемой для любого, кто найдёт флешку.

**Проверено на:** Kali 2026.3 Live ISO · 32 GB+ USB 3.0 · записано из Windows
**Сложность:** ★★☆☆☆ · **Время:** ~20 минут · **Риск:** каждая команда нацелена на USB-флешку — определишь не тот диск и сотрёшь свой накопитель

---

## 🎯 Что ты получишь в итоге

В меню загрузки USB появятся три пункта:

```
Live system (amd64)                        ← one-off, everything lost on shutdown
Live system (amd64) persistence            ← plaintext persistence
Live system (amd64) encrypted persistence  ← the goal: passphrase first, then boot
```

Всё, что ты устанавливаешь, настраиваешь и сохраняешь в `~`, переживает перезагрузку. Если флешку украдут, злоумышленник увидит только контейнер LUKS, который не сможет открыть.

## 🧠 0. Сначала три понятия

Пойми эти три вещи — и каждая команда ниже станет очевидной, а не чем-то, что копируют вслепую.

**① Kali Live работает только для чтения.**
При каждой загрузке система распаковывает корневую файловую систему из ISO в оперативную память. Всё, что ты изменишь, исчезает при выключении. Именно поэтому персистентность и существует.

**② Персистентность = один раздел с меткой `persistence` + один файл.**
При загрузке live-boot сканирует диски в поисках раздела с `LABEL=persistence`, а затем накладывает его поверх корневой файловой системы, доступной только для чтения. Чтение идёт из ISO, запись попадает на флешку. Разделу нужен всего один файл с именем `persistence.conf`, содержащий одну строку: `/ union`.

**③ Зашифрованная персистентность = тот же раздел, обёрнутый в LUKS.**
При загрузке initramfs запрашивает парольную фразу, открывает контейнер, отображает его в `/dev/mapper/<name>` и *затем* обращается с ним точно так же, как с обычным разделом персистентности.

Ключевая мысль: **live-boot обращает внимание только на метку. Ему всё равно, лежит ли метка на обычном разделе или на отображении LUKS.**

Итоговая раскладка на флешке:

```
Physical layout
┌──────────────────┬──────────┬────────────────────────────────┐
│ sda1   4.6 GB    │ sda2 4 MB│ sda3   remaining space         │
│ ISO9660 image    │ EFI boot │ LUKS container                 │
│ (read-only)      │          │  └─ /dev/mapper/my_usb         │
│                  │          │       ext4 · LABEL=persistence │
└──────────────────┴──────────┴────────────────────────────────┘
```

## 🧰 1. Что понадобится

| Элемент | Требование | Зачем |
|---|---|---|
| USB-флешка | ≥ 32 GB, USB 3.0+ | персистентность пишет постоянно; дешёвые флешки подвисают и отваливаются |
| Образ | `kali-linux-2026.3-live-amd64.iso` | должен быть **live**, а не installer |
| Записывающая утилита | Rufus (Windows) | использовать **режим DD** |
| Прошивка | Secure Boot отключён | Kali Live не подписан Microsoft |
| Парольная фраза | хранится в менеджере паролей | потеряешь её — данные пропадут навсегда |

**О скачивании:** в официальном каталоге `https://cdimage.kali.org/current/` образ Live распространяется **только как `.torrent`** (около 443 KiB) — именно installer поставляется в виде `.iso`. Использование BitTorrent-клиента здесь — обычный путь, а не обходной манёвр для сломанного зеркала.

**Проверь скачанный файл** — повреждённый ISO это самый коварный режим отказа:

```powershell
# Windows PowerShell
certutil -hashfile .\kali-linux-2026.3-live-amd64.iso SHA256
```

```bash
# Linux / macOS
sha256sum kali-linux-2026.3-live-amd64.iso
```

Сравни символ за символом с `https://cdimage.kali.org/kali-2026.3/SHA256SUMS`.

## 💾 2. Запись ISO (режим DD)

В Rufus: **Device** → твоя флешка · **Boot selection** → ISO · когда появится диалог режима, выбери **DD Image mode** · Start.

> ⚠️ **Никогда не трогай ползунок «Persistent partition size».**
> Rufus реализует персистентность, патча дистрибутивы на базе casper (Ubuntu, Mint). Kali использует live-boot + isohybrid, поэтому ползунок переписывает разметку разделов, GRUB больше не находит ядро, и ты оказываешься в голом приглашении `grub>`. Начни запись заново с нуля.

Когда запись закончится, **не** открывай флешку никаким инструментом разметки Windows (Disk Management, DiskGenius, AOMEI…).

## 🖥️ 3. Первая загрузка и определение флешки

Загрузись с USB и выбери **`Live system (amd64)`** (обычный пункт).

> Почему не пункт с персистентностью? Раздела персистентности ещё нет, так что это было бы бессмысленно — а разделы нужно изменять из **сессии без персистентности**, иначе overlay активно использует диск, который ты редактируешь.

Открой терминал и выведи список дисков:

```bash
lsblk -o NAME,SIZE,RM,FSTYPE,LABEL,MOUNTPOINTS
```

Определи флешку по трём признакам вместе:

- `RM=1` (съёмный)
- один из её разделов смонтирован в `/run/live/medium` или `/lib/live/mount/medium` (это работающий ISO)
- ёмкость совпадает с флешкой в твоей руке

Заодно проверь режим записи:

```bash
lsblk -f
```

- ✅ `sda1` имеет `iso9660`, а `sda2` — `vfat` (~4 MB) → **режим DD, всё верно**
- ❌ один большой раздел `vfat` → записано в режиме ISO, вернись к шагу 2

**Автоопределение** (рекомендуется — одна опечатка здесь сотрёт твой ноутбук):

```bash
medium=$(findmnt -no SOURCE /run/live/medium 2>/dev/null || findmnt -no SOURCE /lib/live/mount/medium)
usb=/dev/$(lsblk -no PKNAME "$medium")
echo "USB = $usb"
lsblk "$usb"
```

Вывод выглядит примерно так:

```
NAME   MAJ:MIN RM   SIZE RO TYPE MOUNTPOINTS
sda      8:0    1  57.3G  0 disk
├─sda1   8:1    1   4.6G  0 part /run/live/medium
└─sda2   8:2    1     4M  0 part
```

Закрепи его в переменной — все последующие команды ссылаются на `$usb`, поэтому опечатка не попадёт на другой диск:

```bash
usb=/dev/sda     # используй то, что увидел выше
```

## 🧩 4. Создание третьего раздела

Посмотри текущую таблицу:

```bash
sudo fdisk -l $usb
```

Ожидается `Disklabel type: dos` и два раздела: примерно 4.x GB (ISO) и несколько MB (EFI).

Запусти редактор:

```bash
sudo fdisk $usb
```

Нажимай клавиши по порядку:

| Клавиша | Значение |
|---|---|
| `p` ↵ | вывести таблицу, убедиться, что есть только sda1 + sda2 |
| `n` ↵ | новый раздел |
| `p` ↵ | primary |
| `3` ↵ | номер раздела (Enter принимает значение по умолчанию 3) |
| ↵ | первый сектор: по умолчанию, сразу за sda2 |
| ↵ | последний сектор: по умолчанию, до конца диска |
| `w` ↵ | записать и выйти |

> ⚠️ Почему `fdisk`, а не GParted?
> Записанный в режиме DD гибридный ISO — это «диск внутри диска»: всё устройство видится как один огромный блок ISO9660, поэтому GParted показывает всю флешку как один раздел и не видит свободного места. Это не баг, а природа образа. `fdisk` редактирует нижележащую таблицу разделов напрямую и работает нормально.

**А теперь шаг, на котором застревает большинство.**

После `w` ты, скорее всего, увидишь:

```
The kernel still uses the old table.
The new table will be used at the next reboot.
Re-reading the partition table failed.: Device or resource busy
```

Причина проста: **ты загрузился с этой самой флешки, поэтому `sda1` всё ещё смонтирован**, и ядро отказывается перечитывать таблицу. Дальше:

```bash
lsblk $usb
```

- **`sda3` есть** → продолжай с шага 5
- **её нет** → не борись с `partprobe` (он падает с тем же «busy»), просто **перезагрузись снова в `Live system (amd64)`**. Таблица уже на диске; ядро подхватит её при загрузке. Определи диск заново (шаг 3), убедись, что `sda3` существует, и продолжай.

## 🔐 5. Шифрование с помощью LUKS

Последняя проверка безопасности — выведи устройство и посмотри на него, прежде чем нажимать Enter:

```bash
[ -b ${usb}3 ] && lsblk -o NAME,SIZE,TYPE ${usb}3
```

Затем:

```bash
sudo cryptsetup --verbose --verify-passphrase luksFormat ${usb}3
```

Взаимодействие:

1. `WARNING! This will overwrite data on /dev/sda3 irrevocably.` → введи **`YES`** (заглавными; `yes` не принимается)
2. `Enter passphrase for /dev/sda3:` → твоя парольная фраза
3. `Verify passphrase:` → ещё раз

**Как выбрать парольную фразу (именно здесь люди и ошибаются):**

- Разблокировка происходит в initramfs, где раскладка клавиатуры — **US English**. Символы, которые меняются между раскладками (`ä`, `@` на немецкой клавиатуре, …), наберут не то, что ты думаешь
- Рекомендуется: **12+ символов, только строчные буквы и цифры**, либо длинная парольная фраза, которую ты действительно можешь произнести
- `--verify-passphrase` просто спрашивает дважды, чтобы защитить от опечаток

> Это парольная фраза, которую ты вводишь при каждой загрузке. **Потеряешь её — данные не восстановить.** Держи копию в менеджере паролей.

## 📦 6. ext4 + метка persistence

Открой контейнер:

```bash
sudo cryptsetup luksOpen ${usb}3 my_usb
```

Введи парольную фразу. При успехе `/dev/mapper/my_usb` — это *расшифрованное* устройство — **все форматирования и записи с этого момента нацелены на него, а не на `${usb}3`**.

```bash
sudo mkfs.ext4 -L persistence /dev/mapper/my_usb
sudo e2label /dev/mapper/my_usb
```

`e2label` должен вывести:

```
persistence
```

> Почему метка обязана быть `persistence`? live-boot находит раздел персистентности по `LABEL=persistence`. `persist`, `Persistence` или `persistence ` (с пробелом на конце) молча игнорируются.

## 📝 7. Запись persistence.conf

```bash
sudo mkdir -pv /mnt/my_usb
sudo mount -v /dev/mapper/my_usb /mnt/my_usb
echo "/ union" | sudo tee /mnt/my_usb/persistence.conf
sync
```

`/ union` означает: наложить всю корневую файловую систему `/` на этот раздел, чтобы все записи попадали сюда.

> ⚠️ Создавай файл через `echo` внутри Linux. Если создать его в Windows Notepad, он получит CRLF-переводы строк, live-boot разберёт `/ union\r`, такого пути не существует, и персистентность молча не заработает. Это самая распространённая ошибка.

## ✅ 8. Проверка

Обе проверки должны пройти:

```bash
sudo blkid /dev/mapper/my_usb
```

```
/dev/mapper/my_usb: LABEL="persistence" TYPE="ext4"
```

```bash
xxd /mnt/my_usb/persistence.conf
```

```
00000000: 2f20 756e 696f 6e0a                      / union.
```

Файл должен заканчиваться на `0a` (LF). Если видишь `0d0a`, это CRLF — удали файл и создай заново.

Ещё одна проверка, удобная для быстрого взгляда:

```bash
stat -c '%s bytes' /mnt/my_usb/persistence.conf   # должно быть 8
```

## 🔒 9. Размонтирование и закрытие

```bash
sudo umount -v /mnt/my_usb
sudo cryptsetup luksClose my_usb
sudo reboot
```

Порядок важен: **сначала размонтируй файловую систему, потом закрывай отображение** — иначе получишь `Device or resource busy`.

## 🚀 10. Загрузка и проверка

Выбери **`Live system (amd64) encrypted persistence`** в меню загрузки.

У тебя должно появиться приглашение примерно такого вида:

```
Enter passphrase for /dev/sda3:
```

Введи парольную фразу, дойди до рабочего стола и проверь две вещи.

**① Данные действительно зашифрованы** (украденная флешка бесполезна):

```bash
lsblk -f
```

`sda3` должен показывать `crypto_LUKS`, а ниже — отображение `my_usb` с `ext4` и меткой `persistence`.

**② Персистентность действительно работает:**

```bash
echo hello > ~/enc-test
sudo reboot
```

Загрузись снова тем же пунктом, разблокируй, затем:

```bash
cat ~/enc-test     # выводит hello → готово
```

## 🛡️ 11. Усиление защиты

### 11.1 Резервная копия заголовка LUKS

Повреждённый заголовок означает, что весь раздел нечитаем, а находится он в первых нескольких мегабайтах, где одна случайная запись может его уничтожить.

```bash
sudo cryptsetup luksHeaderBackup ${usb}3 --header-backup-file ~/luks-header-backup.img
```

Храни этот `.img` на другой флешке или в облачном хранилище. **Он защищает от повреждения заголовка, но не от забытой парольной фразы.**

### 11.2 Установка nuke-пароля

Сначала установи пакет, который даёт эту возможность (это патч Debian, по умолчанию такой команды не существует):

```bash
sudo apt install -y cryptsetup-nuke-password
sudo cryptsetup luksAddNuke ${usb}3
```

Задай аварийный пароль. Если тебя когда-нибудь принудят разблокировать флешку, ввод этого пароля стирает заголовок LUKS, и никто не сможет расшифровать данные.

### 11.3 Добавление резервной парольной фразы

```bash
sudo cryptsetup luksAddKey ${usb}3
```

### 11.4 Просмотр слотов ключей

```bash
sudo cryptsetup luksDump ${usb}3
```

Перечисляется каждый слот — основная парольная фраза, резервный ключ, nuke-пароль.

## 🩺 12. Устранение неполадок

| Симптом | Причина | Решение |
|---|---|---|
| В меню загрузки нет пункта `encrypted persistence` | под UEFI другая вложенность меню, или неверный ISO | загляни в подменю `Live system`; убедись, что загрузился с флешки |
| `/dev/sda3` отсутствует после `w` | ядро не может перечитать занятую таблицу разделов | перезагрузись в Live (шаг 4) |
| `partprobe` сообщает «busy» | `sda1` флешки смонтирован, потому что ты загрузился с неё | игнорируй, перезагрузись |
| Парольная фраза отклоняется снова и снова | initramfs использует раскладку US; в парольной фразе есть символы, зависящие от раскладки | перезадай ключ обычными ASCII-буквами и цифрами |
| Изменения исчезают после перезагрузки | загрузился обычным `Live system`; или неверная метка; или CRLF в конфиге | повтори обе проверки из шага 8 |
| `blkid` не показывает метку `persistence` | неверная метка или форматирование вне отображения | `e2label /dev/mapper/my_usb persistence` |
| `fdisk` предупреждает `GPT PMBR size mismatch` | на флешке осталась старая таблица GPT (сам образ Kali — это DOS-таблица, так что этого быть не должно) | `sudo sgdisk -e $usb`, чтобы перенести резервную GPT, затем снова `fdisk` |
| `luksFormat` говорит «Device is in use» | раздел был автоматически смонтирован | `sudo umount ${usb}3`, повтори |
| Загрузка надолго зависает на `cryptsetup` | это нормально — разблокировка в Live-среде медленная | подожди 10–30 с |

## ⚡ 13. Шпаргалка

Как только `${usb}3` существует, вся последовательность от шифрования до очистки выглядит так:

```bash
usb=/dev/sda                      # определяй заново при каждой загрузке

# шифрование
sudo cryptsetup --verbose --verify-passphrase luksFormat ${usb}3

# открыть, отформатировать, поставить метку
sudo cryptsetup luksOpen ${usb}3 my_usb
sudo mkfs.ext4 -L persistence /dev/mapper/my_usb

# смонтировать и настроить
sudo mkdir -p /mnt/my_usb
sudo mount /dev/mapper/my_usb /mnt/my_usb
echo "/ union" | sudo tee /mnt/my_usb/persistence.conf
sync

# проверка
sudo blkid /dev/mapper/my_usb          # LABEL="persistence" TYPE="ext4"
xxd /mnt/my_usb/persistence.conf       # должно заканчиваться на 0a

# очистка
sudo umount /mnt/my_usb
sudo cryptsetup luksClose my_usb
sudo reboot
```

## ❓ Частые вопросы

**Не хочу шифрование — нужна только обычная персистентность?**
Пропусти `luksFormat` и `luksOpen` из шагов 5–6, выполни сразу `sudo mkfs.ext4 -L persistence ${usb}3`, а затем продолжай с шага 7. Загружайся с пункта `persistence`.

**Вышел новый релиз Kali — придётся всё переделывать?**
Да. Перезапись ISO в режиме DD сбрасывает таблицу разделов, и раздел персистентности исчезает вместе с ней. Сначала скопируй свой `~` с флешки.

**Раздел персистентности заполнен — можно его увеличить?**
Расширь его на свободное место в конце флешки, затем:

```bash
sudo cryptsetup luksOpen ${usb}3 my_usb
sudo cryptsetup resize my_usb
sudo resize2fs /dev/mapper/my_usb
```

**Я забыл парольную фразу LUKS.**
Восстановления нет. Никакого быстрого перебора, и резервная копия заголовка не поможет (она защищает только от повреждения). Именно поэтому парольная фраза должна лежать в менеджере паролей.

**Можно ли «установить» систему, чтобы `apt upgrade` работал нормально?**
Это другой путь: установить Kali на флешку с помощью installer-ISO, обращаясь с ней как с обычным диском. Стабильнее, но каждое обновление ядра требует внимания к GRUB, и флешка изнашивается быстрее. Гибридный Live-подход лучше для переносного инструментария.

**Персистентность износит мою USB-флешку?**
Запись добавляется, но при обычном использовании это не проблема. Избегай безымянных флешек, не заполняй её полностью (переполненный overlay ведёт себя странно) и время от времени проверяй `df -h`.

**Можно ли изменять раздел персистентности, загрузившись с персистентностью?**
Нет. Overlay использует его; переразметка или переформатирование из этой сессии с высокой вероятностью повредят данные. Всегда делай это из обычной сессии `Live system`.
